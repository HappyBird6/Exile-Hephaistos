## 결과

실제 티어·수치별 결과를 보존하면서, 이후 전이 법칙이 완전히 같은 마지막 옵션 추가 단계의 계산만 공유하도록 구현했다. 원본 3목표 사례의 63개 실제 상태와 32개 경로는 그대로 유지하고 계산 상태는 3개, 실제 경로 실행은 8개로 줄었다. 확장한 4목표 사례는 567개 상태·369개 경로를 보존하며 기존 초기 예산 안에서 완료했다. 12개 정상 지원 시나리오는 모두 목표에 도달했고 지원 계획 탐색이 완료되었다.

후보에는 실제 티어와 옵션, 출발 상태별 결과 확률을 직접 표시한다. 계산 가능 상태에서는 사용자가 계속 버튼을 반복 누르지 않아도 기존 허용 예산 단계 안에서 자동으로 이어간다. 최대 한도, 취소, 저장 한도는 자동 반복하지 않는다. 현재 실행 중인 localhost 서비스는 교체하지 않았다.

## 리뷰 발견 사항과 수정

1. **화면 묶음만으로는 계산 폭증이 줄지 않았다.** `TerminalAdditionClasses`가 모든 선택 가능한 마지막 추가 동작과 정확한 결과 질량을 비교해 동등성을 증명한다. 준비·제거·재시도·다음 체크포인트가 남은 경우에는 공유하지 않는다. 증명 실패나 512행 증명 작업 한도 초과는 기존 정확 계산으로 돌아가며 허용 화폐·결과를 삭제하지 않는다.
2. **동등 계산과 실제 아이템을 분리했다.** 대표 실행의 추가 옵션만 각 원래 아이템에 운반한다. 기존 옵션의 티어·수치·fractured 상태, 목표 평가와 모든 구체 경로는 남는다. 소멸한 실패 결과는 정확한 합계 질량으로 보관한다. 서로 다른 방법·출발 상태의 확률은 합산하지 않는다.
3. **공유 실행의 저장·복원과 자원 계수를 보완했다.** 실행 중·완료·예산 중단·예산 확대 후 checkpoint를 각각 복원해 정확한 결과를 비교했다. 실제 상태/방법 수와 계산 상태/실행 수를 구분하고 증명에 남긴 행도 retained 계수에 포함한다. 최대 retained 한도 비교의 경계값도 수정했다.
4. **다시 열 때 결과 행 순서가 달라지는 결함을 수정했다.** API 결과를 종류와 target 순서로 정렬하여 JSON 재로드 전후 방법 결과가 안정적으로 일치한다. 동일한 확률 구간의 표시 변환은 한 응답 안에서 공유한다.
5. **후보를 보기 위해 여러 번 펼쳐야 했다.** 후보 목록은 기본 펼침으로 열리고, 각 후보에 정확한 티어·옵션을 바로 표시한다. 반복되는 전체 아이템 헤더는 제거하고 공통 카드와 오른쪽 선택 아이템에 남겼다. 확률에는 출발 아이템과 동작을 함께 표시한다. 단일 시도와 `N회 이내`를 구별한다.
6. **계속 버튼 반복과 재개 중 취소 경합을 수정했다.** READY는 다음 ADVANCE, 재개 가능한 RESOURCE_BUDGET은 기존 단계의 RESUME으로 이어진다. 같은 거절 revision은 반복하지 않는다. RESUME 요청 중에도 중지할 수 있고 늦게 온 READY 응답이 취소를 덮어쓰지 않는다. 저장된 작업은 사용자의 재개 동작을 유지하고, 가져온 결과는 읽기 전용이다.
7. **지원 범위 밖 목표의 불필요한 탐색을 줄였다.** 한 활성 AND 그룹의 양수 하한 direct explicit 통계에 한해 실제 카탈로그로 필요한 옵션 수의 하한을 증명한다. 중복 통계는 한 번 세고, 한 옵션에 들어 있는 여러 통계도 반영한다. `ceil(필요한 서로 다른 통계 수 / 한 옵션의 최대 통계 포괄 수)`가 4를 넘을 때만 생성 전에 HTTP 422 `GOAL_EXCEEDS_FOUR_EXPLICIT_SCOPE`로 안내한다. 다중 통계·중복 조건·COUNT가 잘못 거절되지 않는 테스트를 추가했다. 목표 수만 세거나 사용자의 목표를 자동 변경하지 않는다.
8. 계산 내부 수치는 6개 언어의 접힌 **계산 세부 정보** 안으로 이동했다. 일반 화면에는 지원 여부·계산 상태·결과와 행동에 필요한 안내를 남긴다.

## 확률을 읽는 기준

모든 확률은 저장소의 검토된 카탈로그·weight·규칙 및 기존 반복 모델에 따른 값이다. 실제 게임 확률의 독립 실측을 주장하지 않는다. 표의 백분율은 인증 구간을 읽기 쉽게 반올림한 값이며 정확한 분자/분모는 증거 JSON/XML에 있다. 누락된 질량 재정규화나 임의 clipping을 추가하지 않았다.

반복 가능한 방법은 **100회 이내** 관측을 사용한다. 준비 동작은 처음 한 번이고 반복 중 아이템 상태·제거 위험·중단 조건을 전이 모델로 반영한다. 상태 의존 시도를 독립 Bernoulli 시도로 치환하지 않았다. SINGLE_PASS는 N 선택과 관계없이 한 번만 수행한다. 여러 단계의 전략 수치와 한 방법의 결과 확률은 다르다. 원본 3목표의 루트 1동작만으로 3목표에 도달하는 확률은 0이며 후속 동작이 필요하다.

후보 화면의 수치는 **해당 출발 상태에서 해당 결과로 가는 질량**이다. 목표 성공을 조건으로 재정규화한 조건부 티어 분포는 구현하지 않았다. 그래프 탐색 완료와 전략 우열 인증 완료도 구분한다. 일부 전략 비교는 PENDING으로 남고, 전역 최적성을 주장하지 않는다.

## 자원·시간·저장 검토

원본 3목표의 기준 결과는 63상태/32방법, 587operations, 347retained, 353ms였다. 변경 후 63/32를 그대로 보존하고 계산3/실행8, 52operations, 191retained이다. 실제 티어를 지운 것이 아니라 중복 실행을 공유한 결과다. 계산 공유 수정 단계 집중 회귀 시간은461ms이며 이전 반복 측정은306~434ms였다. **CPU 또는 응답 속도가 빨라졌다고 주장할 수 없다.** 동등성 증명 자체의 비용도 있다(원본 3목표 4392행, 45ms). 머신 부하와 순서에 영향을 받는다. retained는 논리 레코드 계수이며 실제 heap byte 측정값이 아니다.

계산 공유 단계 실제 API의 4목표 취소→재개→완료→디스크 JSON 재로드 회귀는 ADVANCE 3회, 취소 뒤 사용자가 재개한 것 외 추가 RESOURCE RESUME 0회였다. 최대 ADVANCE3391ms, 취소 확인567ms였다. 과거 측정은 각각3790/530ms였다. 300ms 설정은 계산 slice 목표이며 저장·표시·직렬화와 동기화까지 포함한 응답/취소 지연의 보장이 아니다. 재개가 기존 규칙에 따라 예산을 확대했기 때문에 API 완료 자원 한도는128/256/40000/10000으로 기록된다. 별도 직접 graph 사례는 초기 예산 안에서 완료했다.

설정은 늘리지 않았다: 계산 상태64→128, 경로 실행128→256, retained20000→40000→50000, primitive5000→10000, 활성 작업16, 디스크 작업당64MiB/전체1GiB/256개. concrete 방법 수369를 허용하려고 실행 한도를 올린 것이 아니다. 새 resources 검증은 실제 배열 수와 공유 계산 수를 구별하며 위조된 계수를 거절한다. 기존 resources 없는 응답·코드는 이전 한도를 적용한다.

4목표 API 결과는 약6.2MB다. 6개 언어 카드까지 담은 가져오기 원문은8,573,320byte, `.exile` 코드는83,231byte였다. 기존16MiB 원문/2MiB 압축 안전 한도와 codec은 변경하지 않았다. 큰 결과의 직렬화·UI 처리 비용은 여전히 남는다.
