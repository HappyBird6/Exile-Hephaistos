# 검증·리뷰·제한적 수정

상위: [공통 규칙](MULTI_SESSION_WORKFLOW.md). 증거 형식: [기록](RECORDS.md).

## 범위 검증

기능 작업자는 동작 변경과 결함 재발을 확인하는 테스트를 작성·수정·실행한다. 관리자는 증거 확인과 필요한 통합 검증 실행을 맡으며, 검증 실패를 직접 코드·테스트 수정으로 해결하지 않는다. 단순 문구 수정에 구현을 그대로 복제한 테스트를 만들지 않는다. 테스트를 통과시키기 위해 기대값을 부당하게 약화하거나 검증을 삭제하지 않는다.
프로젝트의 필수 검증을 우선하고 변경 영역·직접 의존 영역부터 확인한다. 범위 지정이 불가능하거나 영향이 넓으면 필요한 전체 검증을 실행하고 이유를 기록한다. 전체 검사에 별도 사용자 지시를 기본 요구하지 않는다.
성공은 실제 종료 코드·요약·대상 상태로 판단한다. 실행하지 못한 항목은 이유와 함께 분리한다. 기존 실패도 근거 없이 기존 문제로 단정하지 않는다.

## SHA와 작업 공간 증거

최종 검증은 자기 변경 commit 후 수행한다. 개발 중 미커밋 검증은 중간 결과이며 최종 통과 증거로 재사용하려면 최종 상태의 동등성을 확인해야 한다.
검증 전후에 SHA·branch·tracked 변경·관련 untracked/ignored 생성물·런타임 버전·의존성 lockfile 해시·명령·종료 코드·로그 위치를 기록한다. 비밀 값은 기록하지 않는다. 로그는 공용 기록 위치에 두어 검증 대상 소스에 섞지 않는다.
깨끗한 Git 상태만으로 충분하지 않다. 검증 결과에 영향을 주는 ignored 설정·생성물·환경변수는 이름과 비밀 없는 식별 정보로 기록한다. 무관한 캐시 전체를 해시하지 않는다. 관련 입력을 확인할 수 없으면 결과 재사용을 금지한다.
검증이 tracked 파일을 바꾸면 원인을 확인한다. 필요한 변경은 commit하고 다시 검증한다. 시작·종료 SHA 또는 관련 입력이 바뀌면 이전 결과를 최종 증거로 사용하지 않는다.

## 결과 재사용

동일 SHA, 동일 관련 입력·검증 명령·런타임 조건이 확인된 결과만 재사용한다. 더 넓은 검증을 좁은 테스트 결과로 대신하지 않는다. 통합·의존성·계약이 달라지면 영향 범위를 다시 검증한다.
리뷰어는 같은 테스트를 습관적으로 다시 실행하지 않는다. 실행 증거가 부족하면 필요한 확인을 관리자에게 요청한다.

## 리뷰 정책

- 사소한 변경: 구현자의 자체 확인을 기록하고 독립 리뷰 생략 가능.
- 일반 변경: 작업 단위별 반복 리뷰 대신 통합된 변경에 독립 리뷰 1회. 도구가 없으면 별도 자체 점검으로 대체하고 독립 리뷰 미실시를 보고한다.
- 고위험 변경: 독립 리뷰 필수. 실행 수단이 없으면 구현·가능한 검증까지 완료한 뒤 반영을 차단하고 사용자 리뷰 또는 정책 판단을 요청한다.
- 독립 리뷰는 구현하지 않은 별도 실행 문맥을 뜻한다. 같은 모델일 수 있으며 정확성을 보증하지 않는다.

리뷰어에게 요구사항·공개 계약·기준/대상 SHA·diff·검증 증거를 제공한다. 구현자의 자기 정당화나 전체 대화는 전달하지 않는다. 두 관점을 각각 판정한다.

| 관점 | 점검 |
|---|---|
| 명세 준수 | 요구사항 충족, 누락·범위 확대·계약 위반 |
| 코드 품질 | 실제 결함, 예외·경계 처리, 보안, 유지보수, 테스트 적절성 |

각 관점은 PASS / FAIL / UNVERIFIED 중 하나다. 해당 없는 관점도 N/A 이유를 남긴다.

| 심각도 | 예 | 처리 |
|---|---|---|
| blocker | 요구사항 위반, 데이터 손실·보안 결함, 실행 불가, 주요 기능 오류 | 수정·재검증 전 완료 및 반영 불가 |
| suggestion | 비동작 개선, 취향에 가까운 이름·구조 제안 | 남기되 자동 범위 확대·반복 리뷰 안 함 |

근거가 불확실하면 UNVERIFIED로 기록하고 필요한 최소 확인을 제시한다. 필수 요구사항의 UNVERIFIED는 완료를 차단한다. 재리뷰는 기존 결함 해결과 수정 diff의 새 위험을 확인한다. 범위가 넓어졌다면 이유를 남기고 확대한다.

## 실패와 수정 예산

자동 수정은 최초 검증 실패 이후 작업 전체 최대 2회다. 한 회는 모인 결함을 수정하고 해당 범위 검증·필요한 재리뷰를 수행하는 묶음이다. 세션 재생성·작업 쪼개기로 예산을 초기화하지 않는다.

1. 결함 ID와 증거·담당·대상 SHA를 기록한다.
2. 관리자는 원래 기능 작업자 또는 소유권을 인계받은 기능 작업자에게 승인 범위의 수정을 위임한다. 사소한 결함이나 충돌도 관리자 직접 수정 예외는 없다.
3. 관리자가 필요한 변경만 재통합하고 새 SHA를 기록한다.
4. 기능 작업자가 영향 범위 테스트를 수행하고 관리자가 증거와 필요한 통합 검증을 확인한다. 리뷰 결함이면 리뷰어가 해결 여부를 확인한다.
5. 결함을 CLOSED 또는 OPEN으로 갱신한다. 잔여 차단 결함이 없을 때만 진행한다.

같은 원인·같은 접근으로 진전이 없으면 2회를 채우지 않고 중단한다. 일시적 읽기·로컬 검증 실패의 재실행은 원인 근거가 있을 때 1회만 허용하고 기록한다. 권한 거부, 원격 쓰기 결과 불명, 운영 데이터 변경은 자동 재시도하지 않는다.
제품 의미를 바꾸는 판단, 비용·파괴적 작업, 승인 범위 밖 변경은 예산이 남아도 사용자에게 묻는다. 독립적인 안전한 작업은 계속할 수 있지만 차단 항목을 숨기지 않는다.
