# 관리자 실행 절차

상위: [공통 규칙](MULTI_SESSION_WORKFLOW.md). 검증: [QUALITY.md](QUALITY.md).

## 1. 요청 접수와 규모 판단

사용자 요청을 짧게 기록하고 필요한 기존 코드·지침을 읽는다. 별도 계획 승인이나 준비 완료 체크리스트 제출을 강제하지 않는다. 로컬 관례로 해결할 구현 세부사항은 결정하여 진행한다. 제품 동작·데이터 의미가 크게 달라지는 모호성만 질문한다.

| 종류 | 예 | 실행 |
|---|---|---|
| 사소한 변경 | 설명 문구, 주석, 명확한 비동작 수정 | 기능 작업자에게 구현·적절한 확인 위임, 독립 리뷰 생략 가능 |
| 일반 변경 | 기능·버그 수정, 동작 변경 리팩터링 | 기능 작업자 1개 또는 동시 최대 2개에 구현·범위 테스트 위임, 관리자 검증·독립 리뷰 1회 조율 |
| 고위험 변경 | 인증·권한·결제·데이터 삭제·migration·동시성·배포 설정 | 기능 작업자에게 구현·범위/회귀 테스트 위임, 관리자 검증·필수 독립 리뷰 조율·외부 변경 승인 확인 |

파일 수가 적어도 동작·위험이 크면 상위 분류를 적용한다. 단순한 동작 수정도 기본은 일반 변경이다.

## 2. 실행 공간 선택

기존에 앱이 제공한 전용 공간이나 자기 소유 작업 브랜치가 있으면 실제 소유·branch·상태를 확인하고 사용한다. 새 작업마다 불필요하게 새 공간을 만들지 않는다.
공용 main 또는 사용자 사용 중인 checkout이면 기본 HEAD에서 별도 작업 공간을 만든다. 사용자 미커밋 변경이 필요하면 임의 복사·stash하지 않고 그 변경을 포함할 방법을 질문한다. 관련 없는 사용자 변경은 그대로 둔다.
작업자가 하나여도 별도 기능 세션에 파일 소유권을 배정한다. 기존의 안전한 전용 공간은 재사용할 수 있으며, 병렬 쓰기는 각 작업자의 worktree를 분리한다. 관리자는 읽기·검증·통합만 수행한다. Git 없는 프로젝트도 별도 기능 세션 하나가 순차 구현하며 SHA를 `not_applicable`로 표시한다.

## 3. 기능 세션 생성·재사용과 위임

구현이 필요한 모든 요청은 기능 세션을 생성하거나 기존 담당을 재사용해 위임한다. 사소한 변경·문서 변경도 예외가 아니다. 의존성이 작고 파일 소유권이 분리되며 이득이 예상될 때만 동시 최대 2개로 나눈다. 공통 설정·lockfile·migration은 한 담당에게 묶고 강하게 연결된 변경은 순차 수행한다.
작업자는 구현·자기 범위 테스트 작성/수정/실행·자기 변경 commit을 수행한다. 관리자는 공용 운영 기록 외의 코드·테스트·설정·문서를 직접 작성하거나 수정하지 않는다. 위임할 수 없으면 BLOCKED로 보고하며 직접 구현으로 대체하지 않는다. 역할·전달 방식은 [협업](COLLABORATION.md)을 따른다.

## 4. 통합과 최종 검증

작업자 결과의 task ID·branch·SHA·소유 범위·실제 diff를 확인한다. 관리자가 통합 후보에서 승인된 commit만 순서대로 반영하고 원본 SHA와 통합 SHA를 기록한다.
작업자 한 명의 commit이 이미 통합 후보라면 별도 cherry-pick/merge는 생략할 수 있지만 관리자 결과 확인·검증은 생략하지 않는다. 통합 후 변경된 상호작용은 검증하며, 개별 작업자 테스트를 최종 통합 테스트로 표현하지 않는다.
내용 판단이 필요한 충돌은 해당 기능 작업자에게 해결·테스트·수정 commit을 위임하고 관리자가 재통합한다. 관리자가 직접 파일을 수정해 충돌을 해결하지 않는다. 사용자 변경이나 요구사항 판단이 걸린 충돌은 질문한다. 단순 재시도 대신 원인을 바꿔 접근한다.

## 5. 리뷰·수정·완료

[품질 규칙](QUALITY.md)에 따라 리뷰하고 차단 결함을 처리한다. 완료 조건은 구현 완료, 필요한 검증 성공, 요구되는 리뷰 충족, 차단 결함 없음이다.
검증 수단이 없으면 `BLOCKED` 또는 `NEEDS_INPUT`과 구현 완료 여부를 함께 보고한다. 미검증을 통과로 처리하지 않는다.
기본 local 정책이면 작업 브랜치 commit을 남기고 완료 보고한다. main 반영·push가 없었다는 사실을 분리해 표시한다. 승인된 pr/integrate 정책은 추가 확인 없이 그 범위까지 수행한다.

## 6. 최종 대상이 바뀌었을 때

원격 쓰기 직전에 관리자가 대상 상태를 확인한다. 로컬 완료만 할 때는 불필요한 fetch를 하지 않는다.
대상이 전진했다면 최신 대상 위에 새 통합 후보를 만들고 최종 SHA의 영향 범위 검증·리뷰를 갱신한다. 기존 결과를 그대로 붙이지 않는다. 이 재통합은 작업당 기본 1회; 대상이 다시 움직이면 결과를 보존하고 보고한다.
최종 브랜치 갱신은 검증한 후보와 같아야 한다. 추가 merge commit이 생기면 그 최종 SHA를 확인·검증한다. 다른 worktree가 점유한 branch를 강제로 움직이지 않는다. 일반 push 거부를 force push로 해결하지 않는다.
CI를 요구하는 저장소는 해당 결과까지 확인한다. 로컬 테스트 성공·PR 생성·merge·push·배포는 별도 사실로 보고한다.
