# 1인 개발자 관점 평가

대상: v2.0 · 2026-09-20 · 사람용 자료. AI의 기본 실행 지침으로 로드하지 않는다.

## 판정

조건부 도입 권장. 기존 고정 조직형 명세보다 1인 개발의 설정·인계 부담을 줄였다. 특히 단일 세션으로 시작하고 필요할 때만 작업자를 추가하는 방식이 적합하다. 실제 Codex 프로젝트에서 수행시간·토큰·개입 횟수를 측정한 결과는 아니다. 문서 분석과 시나리오 점검, 포함된 저장 도구의 로컬 검증을 기준으로 평가했다.

## 사용자 목표별 평가

| 목표 | 평가 | 근거와 남은 제약 |
|---|---|---|
| 사용자 개입 감소 | 개선 | 구현 요청에 검증·리뷰·2회 수정 포함. 별도 검증 지시 제거. 고위험 판단·권한 제한·무진전은 여전히 개입 필요 |
| 토큰 감소 | 개선 가능성 높음, 수치 미검증 | 작은 작업 직접 수행, 역할별 문서 로드, 결과 요약, 리뷰 1회, 검증 재사용. 일반 변경의 독립 리뷰 비용은 남음 |
| 1인 개발 적합성 | 개선 | 상시 4개 운영 세션 제거, 관리자에게 Git·테스트 통합, 작업자 최대 2개 |
| 초기 설정 최소화 | 개선 | 목표만으로 local 기본 실행 가능. ID·경로·브랜치·명령 자동 감지. 다중 remote나 명령 부재는 상황별 판단 필요 |
| 안전한 반영·재개 | 유지·보완 | 사용자 변경 보호, SHA와 관련 입력 기록, 단일 작성 잠금, 중복 실행 방지. 기록은 로컬이므로 별도 백업 없이는 장치 손실에 취약 |
| 즉시 사용성 | 문서 기반 사용 가능 | 프로젝트에서 진입 문서를 참조해 사용. 네이티브 설치형 스킬·세션 통신 서버는 포함하지 않음 |

## 1인 개발자로서 좋은 점

- 처음에 세션 네 개와 많은 빈칸을 준비할 필요가 없다.
- 작은 변경은 관리자 한 명으로 끝나며 설정 실패가 원격 작업과 무관한 구현까지 막지 않는다.
- 실패할 때마다 나에게 돌아오지 않고 합의한 범위 안에서 수정한다.
- main 반영·push를 기본으로 강제하지 않는다. 원하면 한 번 지정한 정책을 후속 작업에 재사용한다.
- 리뷰에서는 기능 요구사항 충족과 코드 품질을 별도로 볼 수 있다.
- 완료 보고만으로 무엇이 구현·검증·반영되었는지 구분할 수 있다.

## 여전히 불편하거나 주의할 부분

1. **문서 묶음 자체는 가볍지만은 않다.** 파일을 나눈 것만으로 토큰이 줄지는 않는다. 진입 문서와 현재 절차만 읽는 규칙을 실제로 지켜야 한다.
2. **일반 기능마다 독립 리뷰 1회는 비용이다.** 현재는 품질을 위해 유지했다. 실제 측정 없이 더 줄이면 오류 발견 기회를 잃을 수 있다.
3. **관리자는 단일 병목이다.** 1인 개발에서는 단순성의 이점이 크지만 여러 기능을 동시에 많이 맡기면 대기가 생긴다. 처음부터 작업자 수를 늘리지 않는다.
4. **프로젝트별 테스트 선택은 여전히 판단 문제다.** 범위를 잘못 좁히면 회귀를 놓친다. 프로젝트 CI의 필수 검사를 우선하도록 했다.
5. **채팅 이름·세션 통신 지원은 환경마다 다르다.** 불가능한 경우 단일 실행으로 축소한다. 고위험 독립 리뷰는 대신 통과 처리하지 않는다.
6. **두 번의 수정 예산이 항상 충분하지는 않다.** 무한 반복을 막는 기본값이다. 큰 작업은 명확한 하위 작업으로 나누되 기존 실패 예산을 회피하지 않는다.
7. **공통 도구는 최소 범위다.** 저장·잠금만 구현되어 있다. 프로젝트 자동 감지와 Git·세션 조율은 문서에 따라 에이전트가 실행하며 별도의 완전 자동 실행기는 아니다.

## 시나리오를 통한 설계 점검

아래는 명세상 경로를 추적한 결과이며 실제 Codex 실행 테스트가 아니다.

| 상황 | 기대 경로 | 판정 |
|---|---|---|
| 설명 문구 수정 | 직접 수정·적절한 확인·local 완료 | 불필요한 작업자·리뷰 없음 |
| 일반 기능 테스트 실패 | 결함 기록 → 수정 → 범위 재검증 → 리뷰 | 별도 사용자 검증 지시 불필요 |
| 독립적인 FE/BE 변경 | 파일·계약 분리 → 최대 2 작업자 → 관리자 통합 → 검증·리뷰 | 통합 후 검증 누락 방지 |
| 채팅 통신 도구 없음 | 단일 실행, 일반 리뷰 대체 사실 보고 | 존재하지 않는 협업을 주장하지 않음 |
| 인증 변경인데 독립 리뷰 불가 | 구현·검증 결과 보존 → 반영 차단 | 필수 리뷰를 조용히 생략하지 않음 |
| 같은 SHA, 생성 설정 변경 | 관련 입력 불일치 → 결과 재사용 금지 | SHA만 확인하던 빈틈 보완 |
| 관리자 중단·잠금 잔존 | 종료 확인 후 인계 또는 상태 불명 보고 | 중복 관리자 쓰기 방지 |
| 사용자 미커밋 변경 존재 | 관련성 확인, 무관한 변경 보존, 필요하면 질문 | 자동 stash·덮어쓰기 없음 |
| 원격 대상이 다시 전진 | 후보 재검증 1회, 재발 시 보존·보고 | 무한 통합 루프 방지 |

## 수행한 검증

- Markdown 상대 링크와 파일 존재 여부 검사.
- 역할·Git 정책·리뷰 필수 조건·수정 예산·상태 전이 간 수동 일관성 점검.
- state_io.py: JSON 저장·교체, 잘못된 입력 시 기존 파일 보존, 중복 잠금 거절, 다른 소유자 해제 거절, 정상 해제 확인.
- 실 프로젝트 구현, 실제 채팅 제목 변경·메시지 전달, 원격 push, 네트워크 파일시스템 잠금은 실행하지 않았다.

## 도입 후 측정할 것

서로 다른 규모의 작업 5~10개에서 사용자 질문 횟수, 생성된 작업자 수, 중복 검사 횟수, 수정 횟수, 완료 시간, 도구가 제공하는 토큰 사용량을 기록한다. 토큰 값이 제공되지 않으면 추정치를 실측처럼 쓰지 않는다. 작업 난도가 다른 결과를 단순 비교하지 않는다.
먼저 local 정책으로 사용하고, 원하는 검증 품질이 확인된 뒤 PR 또는 integrate 정책을 명시적으로 설정하는 방식이 적절하다.

## 이전 합의의 반영

- 이름 기반 역할 추론을 제거하고 최초 역할 위임 + 실제 ID 연결로 변경.
- 구현 전 별도 준비 완료·승인 단계는 보류 상태 유지.
- SHA 외 검증 작업 공간 기록, 두 관점 리뷰, 결함별 수정·재검증, 문서 분리 반영.
- 이후 합의한 1인 개발 방향에 따라 테스트 전담·Git 전담을 제거하고 실패 즉시 중단을 제한적 자동 수정으로 대체.
- 기존 원본은 v1 보관본으로 ZIP에 포함하며 활성 규칙으로 로드하지 않는다.
