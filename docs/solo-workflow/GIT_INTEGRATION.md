# Git 전용 채팅의 통합 절차

[작업 운영 명세](MULTI_SESSION_WORKFLOW.md)에 추가로 적용한다.

## 권한과 직렬 처리

사용자가 지정한 Git 전용 채팅 하나가 저장소별 최종 통합을 순차 처리한다.
채팅 이름만으로 담당을 정하지 않는다. 기존 담당이 있으면 재사용하고 인계 시 이전 실행 종료를 확인한다.
사용자가 반영할 작업과 범위를 지시한 뒤 시작한다. 관리자 브리핑이나 인계 파일 자체는 반영 승인이 아니다.
'마스터 반영'은 로컬 merge까지, 'merge·push'는 확인된 원격 대상의 일반 push까지다.
대상 작업·브랜치·remote가 모호하면 해당 쓰기를 보류하고 확인한다. PR·배포는 별도 승인 범위를 따른다.
강제 push·사용자 변경 폐기·보호 규칙 우회·작업 공간 자동 삭제는 하지 않는다.

## 통합 직전 확인

1. 인계 파일의 관리자 연락처·작업 branch·최종 commit·기준 SHA·검증/리뷰·의존 작업을 읽는다.
   실제 diff와 commit을 대조한다. 완료 보고만 믿지 않고 필수 검증·리뷰 및 차단 결함 여부를 확인한다.
2. 최신 로컬 master와 worktree 점유·미커밋 변경·다른 통합 실행 여부를 확인한다.
   사용자 또는 다른 작업의 checkout을 강제로 전환하거나 점유 branch를 우회 갱신하지 않는다.
3. 원격 반영 요청이면 지정 remote를 fetch하여 원격 대상도 확인한다.
   fetch가 불가능하면 원격 최신성을 주장하지 않고 원격 반영을 보류한다. 로컬 반영만이면 원격 최신성을 주장하지 않는다.
4. 확인한 대상 SHA 위에 승인된 commit만 합친 별도 통합 후보를 준비한다.
   승인 작업 밖 commit이 따라오지 않는지 확인하고 원본 commit·기준 SHA·후보 SHA를 기록한다.
5. 기준 이후 변경과 결합 영향을 확인해 필요한 통합 검증과 리뷰를 수행하거나 조율한다.
   기존 증거 재사용은 작업 운영 명세의 소스·관련 입력 동등성 기준을 따른다.
   필수 검증 불가·리뷰 누락·차단 결함이 있으면 master를 갱신하지 않는다. merge 전 필수 CI 등 프로젝트 보호 정책도 따른다.

## 충돌과 변경된 결과

코드·테스트·설정·문서의 내용 판단이 필요한 충돌이나 결함은 원 담당 관리자에게 반환한다.
관리자가 내부 작업자에게 수정·테스트·commit을 맡기고 갱신된 인계 파일을 제공한다. Git 담당은 직접 구현하지 않는다.
통합 중 발견한 결함도 원 작업의 수정 예산을 사용한다. 예산 초과나 무진전은 사용자에게 보고한다.
승인 범위 안의 수정은 필요한 재검증 후 진행한다. 동작·범위가 실질적으로 달라지면 재브리핑 후 사용자 판단을 받는다.
담당이 없거나 결과가 불명확하면 후보와 증거를 보존하고 차단 사유를 보고한다.

## 반영과 결과 보고

1. 최종 반영 직전 대상 SHA가 그대로인지 다시 확인한다. 달라졌으면 새 후보로 영향 검증을 갱신한다.
   대상이 반복해서 바뀌면 직렬 처리 상태를 확인하고 사용자에게 보고하며 검증되지 않은 후보를 반영하지 않는다.
2. 검증된 후보로 로컬 master를 갱신한다. 실제 반영 SHA와 검증 소스의 동등성을 확인한다.
3. push가 지시됐으면 배포 등 외부 부작용의 승인 범위도 확인한 뒤 지정 remote·branch에 일반 push한다.
   거부되면 원격 상태를 확인해 재통합이 필요한지 판단한다. 강제 push로 해결하지 않는다.
   전송 결과가 불명확하면 원격 SHA를 확인하기 전 재실행하지 않는다.
4. 필수 CI 결과를 확인하고 실패는 별도로 보고한다. push 성공을 CI·배포 성공으로 표현하지 않는다.
5. 작업·원본 commit·통합 SHA·검증 결과·로컬 반영 여부·push 결과·남은 문제를 기록하고 사용자에게 요약한다.
   로컬 반영 후 push 실패는 각각 구분하며, 임의 reset이나 재반영으로 상태를 숨기지 않는다.
