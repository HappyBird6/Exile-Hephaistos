# 목표 제작 UI 후속 검증 — 2026-10-19

이 보고서는 독립 리뷰 이후 추가 요청된 희귀도 제목 위치, 단발/반복 표기, 엑잘 결과 그룹화, 시작·목표 개별 초기화를 다룬다. 최초 제작 경로와 10개 이상 실제 카탈로그 시나리오의 상세 근거는 `docs/goal-planner-independent-review-2026-10-19.md`에 보존되어 있다.

## 변경과 판단

- 희귀도 필터의 절대 위치 legend에 기준 컨테이너가 없어 화면 왼쪽 위로 벗어나던 문제를 `.goal-filter-rarity { position: relative }`로 수정했다. 이 필터는 **목표 결과로 허용하는 희귀도**이며 시작 아이템의 희귀도와 별도다. 선택 기능은 유지한다.
- 서버가 `executionMode`와 첫 시행 `cycles: 1` 관측을 제공한다. 첫 시행 후 살아 있는 반복 질량이 있거나 실제 두 번째 사이클에 진입한 방법만 반복으로 분류한다. 단발 방법은 첫 시행 확률과 실제 화폐 비용을 표시한다. 단발 엑잘에 100회라는 이름을 붙이거나 성공률을 100%로 올리지 않는다.
- 반복 방법만 N=100/300/500을 선택할 수 있다. 준비 비용은 `initialUses`, 시행 비용은 `cycleUses`를 그대로 사용하며 준비 비용에 N을 곱하지 않는다. 상태 의존 확률 모델과 유한 관측의 의미를 변경하지 않는다.
- 엑잘 결과는 동일 source와 동일 method 안에서만 화면용으로 묶는다. 다른 화폐·징조·출발 상태·방법은 합치지 않고, Essence 선행 작업이 포함된 방법도 개별 표시한다. 정확한 아이템, tier, roll, 목표/부분 진행/손실 구분과 후속 경로는 유지한다. 합성 평균 아이템을 만들지 않는다.
- 그룹 확률은 같은 방법의 상호 배타적 결과를 kind별로 정확한 유리수로 더한다. 중복 결과 행은 거부한다. 다른 방법의 확률을 더하거나 누락 질량을 재정규화하지 않는다. 그룹 설명에 해당 source에서 방법을 시도했을 때의 조건부 확률임을 명시한다.
- 그룹에서 개별 결과를 선택하면 오른쪽 상태와 화폐 경로가 그 정확한 결과로 연결된다. 선택하지 않은 다른 결과는 접힌 상태를 유지할 수 있고 전체 펼치기도 제공한다. 원본 그래프 데이터는 삭제하지 않는다.
- 시작 초기화는 선택 베이스·현재 아이템 레벨을 유지하고 해당 베이스의 초기 희귀도/옵션/품질 작업 상태로 되돌린다. 목표 입력은 유지한다.
- 목표 초기화는 시작 아이템을 유지하며 빈 AND 그룹, 레벨 범위 없음, NORMAL/MAGIC/RARE 전체 허용으로 되돌린다. 두 초기화 모두 기존 계산 요청과 결과를 무효화하고 즉시 해당 입력을 저장한다. 이전 비동기 입력 응답은 revision/abort 처리로 폐기한다. 사용자의 실제 브라우저 저장값을 강제로 초기화하지 않았다.
- 6개 언어를 유지했다. 새 기본 제작 예제를 추가하지 않았다.

## 기본값 질문에 대한 답변

“매직 생명력 → 생명력/카오스 저항/냉기 저항”은 초기 기본 설정이 아니다. 저장 데이터가 없는 시작은 일반 Solar Amulet, 아이템 레벨 82, 기본 Spirit 15 implicit, 명시 옵션 없음이다. 목표는 빈 AND, 희귀도 3종 허용, 아이템 레벨 제한 없음이다. 24시간 유효한 저장 입력이 있으면 복원하므로 질문의 조합은 저장 입력에서 나올 수 있다. 브라우저에 연결되지 않아 사용자의 실제 localStorage 내용은 확인하지 않았다.

## 한계 및 보존

- 지원 브라우저 inventory가 `apps: [], browsers: []`라 로컬 UI의 실제 클릭·픽셀 배치를 검증하지 못했다. 첨부 이미지는 확인했으며, React DOM 상호작용 테스트와 HTTP/파일 해시 검증을 수행했다. CSS 위치 수정의 실브라우저 최종 시각 확인은 남아 있다.
- 전역 최적 경로라는 주장은 하지 않는다. 반복의 관측 한도, 미지원 확률/효과 구분은 기존 모델을 따른다.
- npm의 기존 high 취약점 1건 경고와 큰 번들 경고는 남아 있다. 이번 범위에서 의존성이나 잠금 파일을 임의 변경하지 않았다.
- 원격 push·merge·외부 배포는 하지 않았다. 사용자 PC의 localhost app/frontend만 교체했다. 원본 환경파일, 기존 DB/Redis와 저장 작업은 보존했다.
- 이번 수정에서 Windows 실행 스크립트나 Compose 원본 설정을 변경하지 않았으므로 Python 스크립트 검사는 재실행하지 않았다. 실제 반영용 Compose 조합은 `config --quiet`로 검사했다.

## 중간 실패와 복구

첫 프런트 검증 환경 복사에서 표시 데이터 검사에 필요한 docs evidence가 빠져 pretest가 실패했다. 필요한 로컬 근거만 추가해 다시 실행했다. 이후 기존 복원 테스트의 “반복 방법이 없어도 N 선택기가 있어야 한다” 가정이 요구사항과 충돌해 실제 반복 CHAOS 방법 fixture를 넣고 기존 복원 assertions를 유지했다. 추가 초기화 테스트는 API 정규화 아이템(null/false 기본 필드 포함)과 UI 원본을 직접 비교해서 실패했으며, 초기화 전후 동일한 저장 형식 원본끼리 비교하도록 바로잡았다. 어떤 실패도 skip이나 확률 oracle 완화로 숨기지 않았다.

로컬 컨테이너 교체는 최초 자동 검토에서 deploy 금지로 거부되어 실행되지 않았다. 기존 인계의 명시적 localhost 반영 승인과 원격 금지 범위를 다시 확인한 후 동일 작업의 재검토가 승인되어 완료했다. 우회 실행은 하지 않았다. 실제 API 검증 중에는 16개 저장 작업 상한으로 네 번째 작업 생성이 429 JOB_CAPACITY를 반환했다. 이번 실행에서 생성한 완료 작업 3개만 별도 증거 폴더로 옮긴 뒤 해당 미실행 사례만 재검증했다. 마지막 작업도 보관하고 기존 작업 13개는 보존했다.
