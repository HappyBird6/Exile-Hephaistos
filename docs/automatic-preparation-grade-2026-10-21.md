# 준비 화폐·진화·제왕 추가 수정 및 검증

현재 상태: 아래 반영 전 검증을 마친 v4를 QA 18080/18081에 반영했다. 추가 사용자 요청으로 기존 8081 프런트만 중지했고 8080 백엔드는 유지했다. 아래의 미배포 기록은 교체 승인 전 시점의 이력이다.

이 문서는 앞선 v3 검증 보고서 이후의 추가 요청을 기록한다. 사용자 테스트 중인 QA 18080/18081 및 운영 8080/8081은 재시작하거나 교체하지 않았다. 아래 변경은 작업 트리 파일과 격리 검사에만 존재한다.

## 구현한 정책

- 카오스를 쓰기 위한 준비용 엑잘티드 오브(`EXALTED`)와 제왕의 오브(`REGAL`)는 징조 없는 방법만 남긴다. 다른 화폐를 위한 준비나 목표 옵션 획득까지 징조를 모두 제거한 것은 아니다.
- 이는 세 준비 분포가 같다는 증명이 아니라 사용자가 정한 재료 정책이다. 전달받은 첫 이미지의 5.81% / 5.75% / 5.85%를 합산·평균·동일시하지 않는다. 남은 일반 준비 방법의 실제 전이 확률을 그대로 계산한다.
- 일반 목표 획득용 제왕에도 엑잘과 같은 분포 비교를 적용한다. 우측 대관식의 징조(`OMEN:DEXTRAL_CORONATION`)와 좌측 대관식의 징조(`OMEN:SINISTRAL_CORONATION`) 중 실제 목표에 유리한 후보를 우선한다. 동일 전이이면 일반 제왕만 남긴다. 모든 결과가 이미 전체 목표를 확실히 끝내는 경우도 추가 징조를 쓰지 않는다. 부분 목표 이후의 경로가 다른 경우는 단순 확률 동률만으로 제거하지 않는다.
- 진화의 오브(`TRANSMUTATION`)는 목걸이의 일반→마법 등급 상승 목적(`RARITY_UPGRADE`)만 조건부 허용한다. 연금술의 오브(`ALCHEMY`), 상급·완벽한 진화는 제외를 유지한다.
- 기존 Workbench의 진화 전이와 후보 풀을 재사용했다. 일반 출발에서는 진화를 준비 단계로 두고 제왕 등 유효한 후속 획득 작업을 연결한다. 진화의 중간 마법 상태만으로 희귀 목표를 달성했다고 처리하지 않는다.
- 카오스 100회 최초 성공, 퀄리티, 보류한 말소·절사 징조 정책과 자원 한도는 유지했다.

정책 버전은 `approved-187-2026-10-21-rarity-v4`이며, 187개 항목은 USE 33 / CONDITIONAL 16 / EXCLUDED 109 / DEFERRED 29이다. 후보는 49개다. 소스 ruleset은 `reviewed-equipment-20261009-v2-debb3f07052d54419a4732f49d9febf78508e23cd69a489698c5e81be80597f7`이다. 현재 서비스가 실행하는 v3 ruleset과 구분해야 한다.

주요 코드: `AutomaticCurrencyPolicy`, `AutomaticCraftingAction.candidates`, `GoalDirectedPlanner.choices/preferAddition`, `WorkbenchSimulator.automaticPlan`, `AutomaticMethodExecution.transition`. 정책 표에 진화의 사용 조건을 기존 6개 언어로 안내했다.

## 확인한 검사

- 최종 Docker 집중 검사: 81개 중 78개 통과, 기존 제품 시나리오 05/06/07 세 개 실패. 오류·건너뜀은 없다.
- 새 준비·제왕 검사 5개 전부 통과: 준비용 일반 엑잘/제왕 각각 한 방법, 목표 획득용 유리한 제왕 징조, 동일 효과의 일반 제왕, 전체 목표가 확실히 완료되는 경우의 불필요한 징조 제외, 정확한 진화→제왕 경로.

## 티어를 속성 하나의 분포로 표현하는 질문

가능하며, 목표 판정과 가능한 후속 작업에 차이가 없는 티어를 별도 후보 행으로 계속 보여줄 필요는 없다. 차이가 있는 경우에도 반드시 한 티어를 대표로 골라야 하는 것이 아니다. 속성 안에 정확한 티어·수치 분포를 두고 성공/실패 조건에 따른 분포와 가중치를 보존할 수 있다.

현재 코드의 차이는 다음과 같다.

- `TierCell.Variant`는 이미 modifier ID, 수치 구간, 정확한 유리수 확률을 가진다. `TierPartition`과 `DeferredItem`은 다른 계산 경로에서 이런 분포를 사용한다.
- 자동 경로의 `AutomaticCraftingKernel.expand`는 스칼라 구간을 합치지만, 서로 다른 티어 ID가 들어간 `ItemState`는 서로 다른 키로 남긴다. `AutomaticMethodGraph`도 그 상태를 노드로 보존한다.
- `TerminalAdditionClasses.prove`는 후속 추가 작업의 법칙을 실제로 비교해 같은 계산을 공유한다. 공유되더라도 `GroupedMethodGraph`의 후보 상세 표는 `b.nodes`와 source ID를 순회하므로 같은 라벨·확률을 반복 표시할 수 있다. 계산 공유와 분포 단위 표시가 끝까지 연결되지 않은 부분이다.

부모가 확인해 전달한 두 번째 사진은 source 2, 6, 8, 9, 12, 13, 15에 같은 엑잘+우측 찬미 라벨과 0.11%가 반복된다. 표시가 같다는 사실만으로 전체 전이가 같다고 확정할 수는 없지만, 차이가 없는 티어·상태를 한 분포로 묶자는 요구는 타당하다. 동일한 도달 분포의 티어 가중치를 `w(t)`라 하면 확률은 `Σ w(t) × P(결과|t)`로 유지해야 한다. 각 조건부 확률이 같은 q이면 합계도 q이며, 행 수만큼 q를 더하지 않는다. 서로 다른 제작 전략의 확률도 합산하지 않는다.

최소 티어·수치 목표에서는 통과/실패한 티어의 조건부 분포를 유지해야 한다. 제거·교체 후에는 속성 간 상관관계와 실제 남은 후보 풀을 유지해야 한다. 반면 현재 자동 탐색에서 보류한 절사 징조나 제외한 상급 화폐를 이유로 모든 티어 분리를 정당화해서는 안 된다. 실제로 도달 가능한 작업만 기준으로 동등성을 판단해야 한다.

제안은 두 층이다. UI에서는 같은 계산·출처 묶음의 행을 하나로 보이고 상세에서 티어 분포를 펼친다. 계산에서는 자동 경로의 구체 상태 키를 조건부 분포와 연결한다. 후자는 앞서 논의한 조건부 상태 표현 확장과 같은 문제이며, 이번에는 큰 구조 변경을 하지 않았다. 사진의 표시값만 보고 임의로 티어를 합치거나 숫자를 중복 합산하지도 않았다.

## 첨부와 남은 검증

사용자 첨부 이미지 두 장를 지원 경로로 준비했다. 첫 이미지의 공식 helper 실행은 Windows의 필수 파일 메타데이터 기록 기능(`os.setxattr`) 미지원으로 실패했고, 최종 로컬 파일 존재 검사도 false였다. 두 번째 파일에 같은 실패를 반복하거나 다른 전송 방식으로 우회하지 않았다. 따라서 이 작업자가 로컬 픽셀을 직접 확인했다고 주장하지 않는다. 사진 설명은 부모가 실제 확인해 전달한 내용을 사용했다. 다운로드 URL·완료 토큰은 보고서에 포함하지 않는다.

추가로 남은 항목은 v4 전체 백엔드 검사, 변경된 준비 규칙의 정상 최대 예산 검사, 새 정책으로 교체하기 전 현재 QA가 저장하는 v10/v3 결과의 읽기 전용 호환 확인이다. 기존 v8/v9 읽기 검사는 통과했지만 그것만으로 v10/v3 호환까지 검증했다고 말할 수 없다. 일반 출발의 복합 진화→제왕 변형은 전체 방법 확률이 나온 뒤의 UI 우선순위도 추가 확인해야 한다. 현재 직접적인 목표 제왕 후보의 분포 비교·순서는 검사했다.

증거는 작업 트리 옆 `../evidence/grade-focused-final-tests`, `grade-focused-final-report`, `grade-normal-tests`, `grade-frontend-results.xml`에 있다. 브랜치와 이전 변경을 유지했으며 push·현재 서비스 교체·데이터 삭제는 하지 않았다.


## 추가 검증과 최종 보완

이 절은 위 1차 체크포인트에서 미실시로 남긴 항목의 후속 결과다. v4를 사용자 테스트 중인 QA나 운영에 반영하지 않았다.

- 실제 QA v3의 품질 30과 카오스 완료 저장 결과를 읽기 전용으로 복사했다. `legacy-v10/` 테스트 자료는 소유자를 테스트 소유자로 바꾸고 만료만 연장했다. 파일의 나머지 실행 기록과 확률은 원본 그대로다.
- v10 그래프이면서 알려진 `approved-187-2026-10-21-goal-v3` 결과만 별도 읽기 전용 경로로 연다. v3 목표 카탈로그 서명은 현재 데이터와 v3 ruleset으로 다시 만들어 확인한다. 일치할 때만 현재 평가용 카탈로그로 검증하며, 원래 요청과 저장 문서는 고치지 않는다. 데이터 정의가 달라지거나 알 수 없는 실행 버전이면 거부한다.
- 품질 판정은 새 그래프와 같은 함수를 사용한다. 목표 30의 시작 상태를 완료로 오인하지 않고, 실제 40 작업 후 상태만 맞게 판정한다. 카오스의 남은 생존 질량은 원래 `RETRY` 표시와 null 대상으로 보존한다.
- 실제 v3 노드·방법·확률·원래 요청 비교, 저장 바이트 불변, ADVANCE/RESUME/CANCEL 거부를 포함하여 기존 v8/v9 호환 검사와 함께 6개가 통과했다. 이전 관찰을 새 정책으로 이어 계산하는 것은 허용하지 않는다.
- 복합 진화→제왕은 완료된 전체 방법의 목표 도달 확률 구간으로 비교한다. 한 후보의 하한이 다른 후보 상한보다 높음이 확인될 때 우선한다. 서로 겹치거나 미완료인 분포는 우열을 단정하지 않는다. 대안은 삭제하지 않으며 수동 선택을 유지한다. 목표 도달 확률만으로 후속 전략 전체의 우월성을 주장하지 않는다.
- 프런트 전체 2,284개가 통과했다. 이후 테스트에 DOM 단언만 더해 관련 5개와 lint/typecheck/format을 다시 통과했다. 실제 컴포넌트에서 유리한 복합 제왕이 기본 선택이며 일반 제왕으로 바꿀 수 있음을 확인했다. 실제 브라우저 시각 검증은 여전히 불가다.

최대 예산의 실제 v4 결과는 [재현 프로브와 관찰](evidence/automatic-preparation-budget/README.md)에 기록했다. 06은 50,026개 레코드로 재개 불가였다. 07은 50,000 예산에서 500,000 단계 후 레코드 33,300개, blockers 없음, 재개 가능 상태로 미완료였다. 07을 최대 자원 한도 때문에 멈춘 것으로 보고하지 않는다. 프로브의 관찰 가드 실패도 그대로 남겼다.

전체 API 회귀 테스트에 남아 있던 준비 방법 3개 단언은 요청된 정책과 충돌했다. 이를 1개로 바꾸고 그 방법의 초기 동작이 징조 없는 일반 엑잘인지 추가로 확인한다. 카오스 100회 완료, GOAL의 구체 대상, RETRY의 null 대상, 엑잘·카오스 사용량에 대한 기존 단언은 유지한다. 05/06/07의 완료 단언은 바꾸지 않는다.

운영 `http://localhost:8081` / API 8080, 기존 QA `http://localhost:18081` / API 18080은 계속 실행 중이다. HTTP/readiness/주요 읽기 API 10건은 모두 200, 기존 컨테이너 8개는 실행 중이며 ID와 시작 시간이 유지됐다. 운영 `.env` SHA-256은 `33C2E0343991D294A322DFA9512AC479B95695B8AF52DEBE8548BD78FCA28F26`으로 같고 원본 master는 40c4a2d 상태다. DB·Redis·볼륨·저장 계산 결과 삭제나 서비스 교체, 원격 push를 하지 않았다. 실행 중 QA ruleset은 계속 v3 `...68910c93...`이며 v4 `...debb3f07...`은 이 파일 및 격리 검사 소스에만 있다. 보존 확인은 `evidence/grade-runtime-final.json`에 기록했다.

실제 브라우저 픽셀 확인과 v4 실행 서버의 HTTP 검사는 미실시다. 사용 가능한 브라우저 표면이 없었고 사용자 테스트 중 서비스 교체는 금지되어 있다. 현재의 HTTP 200은 기존 v3 QA/운영 보존 확인이며 v4 배포 검증으로 해석하지 않는다. v4 적용 시에는 별도 승인된 시점에 이미지를 빌드하고 해당 버전 readiness/API/UI를 다시 검증해야 한다. 큰 티어 분포 구조 개편은 여전히 분석 제안만 남겼다.


## 사용자 승인 후 QA v4 반영

사용자가 QA 교체를 승인했고, 이어 기존 8081 종료를 요청했다. 따라서 QA `app`과 `frontend`만 기존 Compose 환경으로 빌드·재기동했다. 기존 8081은 `exile-hephaistos-frontend-1`만 정상 stop했고 컨테이너는 보존했다. 8080 백엔드 및 운영·QA DB/Redis는 중단하지 않았다. `down`, 볼륨 삭제, 데이터 삭제, 원격 push는 수행하지 않았다.

## 원격 작업 브랜치 보존 검토

사용자 승인 범위는 이 작업 브랜치의 일반 push이며 master 병합·force push·추가 배포는 포함하지 않는다. 검증 당시 미커밋이라는 위 표기는 빌드와 QA 반영 시점의 이력이다. 보존 커밋은 동일한 소스/테스트와 관련 문서로 구성하며 제품 코드는 더 수정하지 않는다. 실행 QA의 최종 소스 지문과 커밋 후보의 코드·계약·테스트 67개 파일이 일치함을 확인했다. 커밋 SHA는 Git 기록으로 식별한다.

소스·테스트·계약 및 이 검증 문서/수동 진단 프로브만 명시적으로 선택한다. `.env`, 자격증명, 로컬 설정, DB/Redis/볼륨 내용, 실제 저장 계산 파일, 백업, JAR/정적 빌드 결과와 대용량 QA 로그·산출물은 저장소 밖에 보존하고 커밋하지 않는다. `backend/src/test/resources/legacy-v10/`의 작은 고정 회귀 fixture 네 개는 자동 QA 검증으로 생성한 테스트 입력·관찰 자료이며 실제 사용자 계산 자료를 포함하지 않는다. 소유자는 기존 테스트 소유자로 치환하고 만료는 고정했으며 개인정보·자격증명을 포함하지 않는다. 이 fixture가 있어야 실제 v3 저장 형식의 읽기 전용 호환 검사를 재현할 수 있다.

전체 검사 결과의 05/06/07 미완료 및 후속 집중 검사 범위, 프런트 2,284개, 저장 호환 6개와 QA HTTP/API 30건의 구분은 위 기록을 유지한다. 원격 보존을 테스트 전체 통과나 이 세 한계의 해결로 해석하지 않는다. 원격 체크 결과는 push 후 별도로 조회한다.
