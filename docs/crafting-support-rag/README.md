# 기존 제작 전략의 RAG 문서

**현재 코드의 판단 조건을 추출한 지식 자료와 별도 RAG 비교 실험이다.** 기존 제작지원은 유지하고 `/support-test`에서 베이스·목표를 정해 문서 기반 전략을 생성한다. 기존 엔진과 후보 및 실행 결과를 비교하며, 실제 모델의 동등성이 입증됐다는 뜻은 아니다.

최초 추출 기준은 `859a29b3`이며 당시 런타임은 `2846ca4b`와 같다. 비교 경로를 연결하면서 공통 입력 검증·판정 함수를 추출했고 기존 후보 선택 정책은 유지했다. 정확한 버전·검색 허용 문서·근거 파일 해시는 [corpus.json](corpus.json)에 기록한다. 문서의 조건은 해당 버전의 **서비스 정책/구현**이며 게임 전체의 공식 규칙을 뜻하지 않는다.

## 추출 기준과 문서 사용법

- 각 문서는 적용/금지 조건, 후보 구성, 종료/예외, 긍정·부정 사례, 근거 코드·테스트를 함께 보존한다. 조건만 검색하고 금지/예외를 잘라내면 안 된다.
- 공통 두 문서는 검색 순위와 무관하게 포함한다. 전략 문서를 검색했으면 그 의존 문서도 함께 제공한다. 제외/보류 제한은 검색 누락으로 해제되지 않는다.
- 조건이 겹치면 [목표 진전 문서](knowledge/goal-progress.md)의 구성 순서를 따른다. 문서의 검색 순위로 화폐 후보를 재정렬하지 않는다.
- 코드와 과거 설명이 다르면 **현재 실행 동작을 명시적으로 추출**하고 불일치를 별도 기록한다. 이것은 그 차이를 사용자 정책으로 승인하거나 버그를 영구 고정한다는 뜻이 아니다.
- 미래의 비용 최적화, 필수/선호/보존 조건 분리, 새로운 화폐 허용은 이번 추출에 추가하지 않는다. 이미 존재하는 확률 우선 정책을 비용 우선으로 바꾸지 않는다.
- 같은 원본을 여러 곳에서 수정하지 않도록 187개 화폐 목록·가중치·슬롯 규칙은 복제하지 않고 기존 JSON/엔진을 참조한다. 자연어 설명은 실행 가능한 정책 파일을 대체하지 않는다.
- 문서 내 코드 이름은 기존 엔진의 판단/행동을 연결하기 위한 식별자다. 임의 코드 실행이나 자유 수식 평가를 지시하는 인터페이스가 아니다.

## 검색과 후보 구성에 필요한 문맥

아이템 텍스트만으로 현재 판단을 재현할 수 없다. 적어도 다음 정보를 기존 엔진에서 얻어야 한다. `StrategyEvidence`가 다음 문맥과 엔진의 적용 가능성·목표 진전·분포 비교 근거를 모델에 제공한다. 기존 후보 정답 목록은 보내지 않는다.

| 문맥 | 의미와 기존 제공 지점 |
|---|---|
| 현재 아이템·카탈로그 | 실제 상태와 규칙 버전. 슬롯·계열·수치·분열·훼손을 보존 |
| 현재 목표와 판정 | 전체 `goal`, 각 행 `entries`, `MATCH/NO_MATCH/UNKNOWN/UNSUPPORTED` |
| 시작 단계 여부 | `initialStage`. 같은 아이템이라도 루트와 후속 노드의 선택은 다름 |
| 변경 가능한 옵션 수 | `AutomaticCraftingKernel.mutableAffixCount`. 분열 제외, 미공개 훼손 포함 |
| 첫 변경 가능 목표 획득 여부 | `GoalDirectedPlanner.choices`의 `acquired`. 분열만 남긴 비교 상태의 판정과 대조하여 계산 |
| 품질 목표·작업 이력 | `qualityGoal`, `abstractQuality`, `quality40`, 품질 상한 유무. 표시 아이템만으로 모두 복원되지 않음 |
| 허용 행동 목록 | `AutomaticCraftingAction.candidates(policy)`의 순서·purpose·징조 |
| 적용 가능성과 결과 | 기존 kernel의 `plan`, `representatives`, `expand` 결과. RAG가 수치나 자격을 추정하지 않음 |

후보 출력은 기존 `Choice(initial, cycle)`와 행동의 `currency/omens/purpose/operation/side/comparison` 의미를 보존해야 한다. 노드/작업 ID를 새로 생성했더라도 비교에서는 의미를 정규화하며, 화폐·징조·순서·purpose·선행 작업·종료 처리를 누락하지 않는다.

## 기존과 같다는 판단 기준

1. 같은 버전·아이템·목표·시작 단계·품질 이력·계산 예산으로 기존 후보 생성기와 새 경로를 비교한다.
2. 후보의 누락/추가뿐 아니라 정렬 순서, 준비/반복 구분, 종료 정책을 비교한다. 순서는 제한된 계산 예산에서 보이는 결과에 영향을 준다.
3. 두 후보 목록을 같은 엔진에 넣어 결과 상태·확률 경계·실패/미해결 질량·소모량을 비교한다.
4. 새로고침/저장 복원 후에도 같은 조건을 재현한다. 작업 중 문서 개정이 바뀌지 않도록 지식 개정을 고정한다.
5. 검색에서 필요한 전략을 놓친 경우, 잘못된 후보를 엔진이 기각한 경우, 기존 코드로 대체한 경우를 각각 기록한다. 기존 코드로 대체한 결과를 RAG 동등성 성공으로 세지 않는다.
6. 알려진 테스트 불일치는 검토 기록에 남긴다. 기대값을 무조건 완화하거나 옛 정책을 활성화해 비교를 통과시키지 않는다.

대표 사례 일치는 모든 가능한 아이템에서의 동등성 증명이 아니다. 신규 장비·규칙 변경 시 같은 경계 검사를 반복한다. 단계별 상세 사례와 직전 검사 결과는 [검토 기록](review-notes.md)을 따른다.

첫 비교에서는 8개 문서를 모두 제공한 기준 실행과 필요한 문서만 검색한 실행을 구분한다. 그러면 문서 해석/후보 구성 오류와 검색 누락을 따로 확인할 수 있다. 전체 문서를 제공해 얻은 일치율을 검색기의 정확도로 보고하지 않는다.

## 유지보수

코드/정책 변경 → 관련 문서와 근거 갱신 → 문서별 사례와 엔진 비교 → `corpus.json`의 근거 소스 해시·개정 갱신 순서로 관리한다. `StrategyKnowledgeTest`가 근거 소스 해시 변경을 감지한다. 문서를 검토한 뒤 해시를 갱신한다. 최초 추출 commit은 이력으로 유지한다. 해시는 선택한 근거 소스의 변경 감지용이며 애플리케이션 리소스 봉인과 연결되지 않는다. 전체 카탈로그·게임 규칙·전이 분포의 동등성을 해시 목록만으로 증명하지 않는다. 새로운 전략 지식을 넣을 때에는 현재 동작의 추출인지 새로운 정책 제안인지 먼저 구분한다.

상위 [설계 문서](../crafting-support-rag-design.md)의 큰 서비스 확장은 후속 검토 대상이다. 현재 우선 범위는 이 문서 묶음의 추출과 기존 후보 생성에 대한 동등성 검증이다.

## 테스트 실행

서버 환경변수에 다음 두 값을 설정하고 백엔드를 재시작한다. Compose는 기존 `.env`를 `--env-file`로 지정하면 `app`에 전달한다. 직접 Java를 실행하는 경우에는 실행 환경에 내보내야 한다. API 키를 프런트엔드의 `VITE_*` 변수나 Git에 넣지 않는다.

```dotenv
SUPPORT_RAG_ENABLED=true
OPENAI_API_KEY=사용자가_직접_입력
```

상단 **제작지원 테스트** 탭(`/support-test`)은 관리자 인증 없이 열린다. 베이스·목표를 입력하고 **입력 확정 → 프롬프트 확인 → 전략 요청**을 누른다. 기존 제작지원의 저장 입력을 덮어쓰지 않는다. 탭 이동·입력 확정만으로 외부 모델을 호출하지 않는다. 오른쪽 응답에는 준비 작업, 반복 작업, 설명이 나온다.

- 기본 모델: OpenAI `gpt-4.1-mini-2025-04-14`. `backend-settings.yaml`의 `support-rag`에서 모델·검색 개수·계산 예산·시간 제한을 관리한다. 공급자 주소는 고정 HTTPS다.
- `GET /api/support-test/rag`는 설정 상태를 조회한다. 입력 확정 후 `POST /api/support-test/rag/prompt`가 관련 문서와 엔진 사실을 준비해 왼쪽에 실제 system/user 프롬프트를 표시한다. 이 단계는 AI를 호출하지 않는다. 사용자가 **전략 요청**을 누를 때만 `/generate`에 서버가 발급한 promptId를 전송하고 오른쪽에 응답을 표시한다. 프롬프트 임의 편집·아이템 트리·비교 통계는 테스트 화면에 넣지 않는다. 기존 관리자 API와 인증 경로를 공유하지 않는다.
- 화면은 시작 단계·관련 문서 검색을 사용한다. 개발용 `POST /api/support-test/rag/compare`에서는 기존 비교 검증을 계속 지원한다. **전체 문서**는 8개 허용 문서를 전부 제공한다. **관련 문서 검색**은 로컬 키워드 검색 후 공통 문서·의존 문서를 합친다. 임베딩/벡터 DB를 사용하는 검색은 아니다.
- 엔진이 적용 가능한 행동과 사실을 계산하고 모델이 문서에 따라 조합한다. 행동 ID·인용·준비/반복 구조·종료 규칙을 검증하고 잘못된 제안을 자동 보정하거나 기존 답으로 대체하지 않는다.
- 개발용 `/compare`는 공통 후보를 기존 실행 엔진에 각각 넣어 최대 현재 관측 범위(100회)까지 상태 분포·확률 경계·재료 소모를 비교한다. 자원 제한으로 끝내지 못하면 `INCONCLUSIVE`다.

## 호출 비용과 실험 범위

- 기본값은 외부 호출 간 최소 30초, UTC 하루 20회다. Redis에서 원자적으로 집계하며 Redis를 사용할 수 없으면 유료 호출을 거절한다. 서버 인스턴스당 비교는 한 번에 1개다.
- 준비된 프롬프트는 최대 8개를 10분 보관한다. 생성은 표시한 프롬프트와 동일한 문서·사실을 사용하며 입력 재계산이나 기존 엔진과의 실행 비교를 하지 않는다. 같은 promptId로 생성한 성공 응답은 재요청 시 외부 호출 없이 반환한다. 만료·퇴출된 ID는 410으로 응답하고 사용자가 프롬프트를 다시 불러와 요청한다.
- 성공적으로 만들어진 비교 응답은 최대 8개를 10분 캐시한다. 같은 아이템·목표·모델·문서 개정·엔진 버전·언어의 재요청은 외부 호출 없이 반환한다. 캐시 응답의 토큰 수는 최초 실행 기록이다.
- 자동 재시도는 하지 않는다. 실패한 외부 호출도 일일 요청 예산에 포함한다. 프롬프트 180KB, 응답 128KB, 출력 최대 6,000토큰을 제한한다.
- Redis 데이터 유실/초기화 시 일일 집계도 사라진다. 이 제한은 공급자 계정의 과금 상한을 대신하지 않는다. 현재 인증 없는 테스트 경로이므로 배포 전 접근 정책을 다시 정하고, 실험하지 않을 때는 `SUPPORT_RAG_ENABLED=false`로 둔다.
- 기본 외부 응답 제한은 45초, 호출 전후 계산 제한은 각 15초다. 계산 중 단일 엔진 연산은 즉시 중단되지 않을 수 있다. 프록시의 해당 경로 응답 제한은 90초이며 시간 설정을 늘리면 함께 검토한다.
- **현재 구체적인 아이템 상태에서 다음 제작 방법 후보를 비교한다.** 목표 도달 전체 루트·최저 비용 추천·후속 노드 자동 RAG 재계산까지 구현한 것은 아니다. 기존 자동 지원이 받지 못하는 아이템 상태는 이 실험도 받지 않는다. 선택적 boolean 상태 플래그 생략은 작업대와 공통인 `ItemStateWireDefaults` 규칙으로 처리한다. 명시적 null·잘못된 타입은 계속 거절한다.
- 공급자 오류·본문 초과·불완전 JSON·타임아웃·동시 요청·누락 후보·잘못된 인용은 자동 테스트한다. 실제 API 키로 생성 품질과 실카탈로그 동등성은 별도로 확인해야 한다. 테스트의 모의 모델이 기존 답을 반환한 결과를 실제 LLM 성공률로 해석하지 않는다.
