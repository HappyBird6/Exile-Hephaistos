# 기존 제작 전략의 RAG 문서

**현재 코드의 판단 조건을 추출한 지식 자료다. 아직 검색기·LLM·실행 엔진에는 연결하지 않았다.** 목적은 전략을 새로 만드는 것이 아니라, 문서를 사용한 후보 생성이 기존 코드와 같은 동작을 하는지 비교할 기반을 마련하는 것이다.

기준 소스는 `859a29b3`이며 런타임 코드는 `2846ca4b`와 같다. 정확한 버전·검색 허용 문서·근거 파일 해시는 [corpus.json](corpus.json)에 기록한다. 문서의 조건은 해당 버전의 **서비스 정책/구현**이며 게임 전체의 공식 규칙을 뜻하지 않는다.

[별도 훼손 추천 코드](reference/abyss-strategies.md)는 주 자동 탐색의 후보 생성과 구분하는 참고 문서다. [불일치와 비교 검증](review-notes.md)은 사람이 검토할 기록이다. 두 문서는 기본 전략 검색 대상에서 제외한다. 문서 전체 폴더를 무조건 수집하지 말고 `corpus.json`의 `retrievalDocuments`만 허용 목록으로 사용한다. 이 규칙을 실행하는 로더는 아직 없다.

## 추출 기준과 문서 사용법

- 각 문서는 적용/금지 조건, 후보 구성, 종료/예외, 긍정·부정 사례, 근거 코드·테스트를 함께 보존한다. 조건만 검색하고 금지/예외를 잘라내면 안 된다.
- 공통 두 문서는 검색 순위와 무관하게 포함한다. 전략 문서를 검색했으면 그 의존 문서도 함께 제공한다. 제외/보류 제한은 검색 누락으로 해제되지 않는다.
- 조건이 겹치면 [목표 진전 문서](knowledge/goal-progress.md)의 구성 순서를 따른다. 문서의 검색 순위로 화폐 후보를 재정렬하지 않는다.
- 코드와 과거 설명이 다르면 **현재 실행 동작을 명시적으로 추출**하고 불일치를 별도 기록한다. 이것은 그 차이를 사용자 정책으로 승인하거나 버그를 영구 고정한다는 뜻이 아니다.
- 미래의 비용 최적화, 필수/선호/보존 조건 분리, 새로운 화폐 허용은 이번 추출에 추가하지 않는다. 이미 존재하는 확률 우선 정책을 비용 우선으로 바꾸지 않는다.
- 같은 원본을 여러 곳에서 수정하지 않도록 187개 화폐 목록·가중치·슬롯 규칙은 복제하지 않고 기존 JSON/엔진을 참조한다. 자연어 설명은 실행 가능한 정책 파일을 대체하지 않는다.
- 문서 내 코드 이름은 기존 엔진의 판단/행동을 연결하기 위한 식별자다. 임의 코드 실행이나 자유 수식 평가를 지시하는 인터페이스가 아니다.

## 검색과 후보 구성에 필요한 문맥

아이템 텍스트만으로 현재 판단을 재현할 수 없다. 적어도 다음 정보를 기존 엔진에서 얻어야 한다. 아래는 의미 계약이며 신규 API 필드를 구현한 것은 아니다.

| 문맥 | 의미와 기존 제공 지점 |
|---|---|
| 현재 아이템·카탈로그 | 실제 상태와 규칙 버전. 슬롯·계열·수치·분열·훼손을 보존 |
| 현재 목표와 판정 | 전체 `goal`, 각 행 `entries`, `MATCH/NO_MATCH/UNKNOWN/UNSUPPORTED` |
| 시작 단계 여부 | `initialStage`. 같은 아이템이라도 루트와 후속 노드의 선택은 다름 |
| 변경 가능한 옵션 수 | `AutomaticCraftingKernel.mutableAffixCount`. 분열 제외, 미공개 훼손 포함 |
| 첫 변경 가능 목표 획득 여부 | `GoalDirectedPlanner.choices`의 `acquired`. 분열만 남긴 비교 상태의 판정과 대조하여 계산 |
| 품질 목표·작업 이력 | `qualityGoal`, `abstractQuality`, `quality40`, 품질 상한 유무. 표시 아이템만으로 모두 복원되지 않음 |
| 허용 행동 목록 | `AutomaticCraftingAction.candidates(policy)`의 순서·purpose·징조 |
| 적용 가능성과 결과 | 기존 kernel의 `plan`, `representatives`, `expand` 결과. RAG가 수치나 자격을 추정하지 않음 |

후보 출력은 기존 `Choice(initial, cycle)`와 행동의 `currency/omens/purpose/operation/side/comparison` 의미를 보존해야 한다. 노드/작업 ID를 새로 생성했더라도 비교에서는 의미를 정규화하며, 화폐·징조·순서·purpose·선행 작업·종료 처리를 누락하지 않는다.

## 기존과 같다는 판단 기준

1. 같은 버전·아이템·목표·시작 단계·품질 이력·계산 예산으로 기존 후보 생성기와 새 경로를 비교한다.
2. 후보의 누락/추가뿐 아니라 정렬 순서, 준비/반복 구분, 종료 정책을 비교한다. 순서는 제한된 계산 예산에서 보이는 결과에 영향을 준다.
3. 두 후보 목록을 같은 엔진에 넣어 결과 상태·확률 경계·실패/미해결 질량·소모량을 비교한다.
4. 새로고침/저장 복원 후에도 같은 조건을 재현한다. 작업 중 문서 개정이 바뀌지 않도록 지식 개정을 고정한다.
5. 검색에서 필요한 전략을 놓친 경우, 잘못된 후보를 엔진이 기각한 경우, 기존 코드로 대체한 경우를 각각 기록한다. 기존 코드로 대체한 결과를 RAG 동등성 성공으로 세지 않는다.
6. 알려진 테스트 불일치는 검토 기록에 남긴다. 기대값을 무조건 완화하거나 옛 정책을 활성화해 비교를 통과시키지 않는다.

대표 사례 일치는 모든 가능한 아이템에서의 동등성 증명이 아니다. 신규 장비·규칙 변경 시 같은 경계 검사를 반복한다. 단계별 상세 사례와 직전 검사 결과는 [검토 기록](review-notes.md)을 따른다.

첫 비교에서는 8개 문서를 모두 제공한 기준 실행과 필요한 문서만 검색한 실행을 구분한다. 그러면 문서 해석/후보 구성 오류와 검색 누락을 따로 확인할 수 있다. 전체 문서를 제공해 얻은 일치율을 검색기의 정확도로 보고하지 않는다.

## 유지보수

코드/정책 변경 → 관련 문서와 근거 갱신 → 문서별 사례와 엔진 비교 → `corpus.json`의 기준 commit·해시·개정 갱신 순서로 관리한다. 해시는 선택한 근거 소스의 변경 감지용이며 애플리케이션 리소스 봉인과 연결되지 않는다. 전체 카탈로그·게임 규칙·전이 분포의 동등성을 해시 목록만으로 증명하지 않는다. 새로운 전략 지식을 넣을 때에는 현재 동작의 추출인지 새로운 정책 제안인지 먼저 구분한다.

상위 [설계 문서](../crafting-support-rag-design.md)의 큰 서비스 확장은 후속 검토 대상이다. 현재 우선 범위는 이 문서 묶음의 추출과 기존 후보 생성에 대한 동등성 검증이다.
